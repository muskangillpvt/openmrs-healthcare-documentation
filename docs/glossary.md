# Glossary — OpenMRS Healthcare Documentation Portfolio

## 1. Purpose

This glossary defines the healthcare, software, privacy, security, and technical-writing terms used throughout the OpenMRS Healthcare Documentation Portfolio.

The goal is to help readers understand unfamiliar terminology and ensure that related documents use terms consistently.

Definitions are simplified for learning purposes. Where a term has a specific legal or technical meaning, the relevant authoritative source should be consulted.

## 2. Healthcare and Medical Record Terms

| Term | Definition | Example or context |
|---|---|---|
| Electronic Medical Record (EMR) | A digital record of health information maintained within a healthcare setting or system. | An electronic system used to store and retrieve patient information. |
| Patient | An individual who receives or may receive healthcare services. | A person whose information is recorded in a healthcare system. |
| Patient record | A collection of information associated with a patient in a healthcare information system. | A record containing identifying details and other authorised information. |
| Patient registration | The process of creating a patient record and entering the required identifying information. | Registering a new patient in an electronic medical record system. |
| Patient identifier | A value used to distinguish or identify a patient within a system or workflow. | An identifier recorded during registration. |
| Demographic information | Information describing a person, such as their name, date of birth, or contact details. | Details entered into a patient registration form. |
| Clinical information | Information related to a person's health, assessment, or healthcare. | Clinical observations or treatment information. |
| Duplicate record | A record that may represent the same individual as another record in the system. | Two records that appear to belong to the same patient. |
| Patient Dashboard | A screen or page that presents information or actions associated with a patient. | A destination shown after registration in the referenced OpenMRS web guide. |

## 3. Software and Application Terms

| Term | Definition | Example or context |
|---|---|---|
| OpenMRS | An open-source medical record platform used in healthcare information systems. | The software used as the case study for this portfolio. |
| Web application | Software accessed through a web browser. | The OpenMRS web application documented in the patient registration guide. |
| Android client | An application that provides access to a system through Android devices. | The separately documented OpenMRS Android client. |
| User interface (UI) | The screens, controls, and other elements through which a person interacts with software. | Forms, buttons, menus, and search fields. |
| Workflow | A sequence of steps used to complete a task. | Searching for a patient, entering details, and saving a record. |
| Configuration | Settings that determine how software behaves in a particular environment. | An installation may have locally configured options or permissions. |
| Software version | A specific release of a software product. | A guide may apply to one version but not another. |
| Environment | The system setup in which software runs. | A development, testing, training, or production environment. |
| Validation | A check that information or an action meets specified requirements. | A form indicating that a required field is missing. |
| Error message | Information displayed when an operation fails or cannot proceed as expected. | A message explaining that submitted information needs correction. |
| Administrator | A person authorised to perform designated system-management tasks. | A system administrator who investigates an access issue. |

## 4. Privacy and Security Terms

| Term | Definition | Example or context |
|---|---|---|
| Privacy | The appropriate handling of information about individuals in accordance with applicable law, policy, and expectations. | Limiting inappropriate disclosure of patient information. |
| Personal information | Information about an identified or reasonably identifiable individual, as defined by the applicable legal framework. | A person's name when linked to other identifying details. |
| Health information | Information about an individual's health or healthcare that falls within the relevant legal definition. | Information contained in a medical record. |
| Sensitive information | Information that receives additional protection under applicable law or policy. | Certain health information may be classified as sensitive information. |
| Access control | Rules and mechanisms that determine which users can access resources and perform actions. | Restricting access to authorised functions. |
| Authentication | The process of verifying an identity. | Signing in to an application. |
| Authorisation | Determining whether an authenticated identity is permitted to perform an action. | Checking whether a user can create a patient record. |
| Permission | An authorisation to perform a particular action or access a resource. | Permission to view or edit a record. |
| Role-based access control (RBAC) | An approach in which permissions are assigned through roles. | A system that associates approved permissions with user roles. |
| Least privilege | The principle of granting only the access necessary to perform an authorised task. | Avoiding unnecessary administrative permissions. |
| Confidentiality | Protecting information against unauthorised access or disclosure. | Preventing patient information from being shared with unauthorised people. |
| Security incident | An event that may compromise the confidentiality, integrity, or availability of information or systems. | Suspected unauthorised access to a patient record. |
| Audit log | A record of selected system events or actions. | A log that may record user activity, depending on the system's capabilities and configuration. |
| Encryption | A process that transforms information so it cannot readily be understood without the appropriate means of decryption. | Protecting information during storage or transmission when correctly implemented. |

## 5. Australian Privacy and Regulatory Terms

| Term | Definition | Example or context |
|---|---|---|
| Privacy Act 1988 | Australian Commonwealth legislation governing the handling of personal information by entities covered by the Act. | A key source for researching Australian privacy obligations. |
| Australian Privacy Principles (APPs) | Principles in the Privacy Act that establish standards for handling personal information by covered entities. | APP 11 concerns the security of personal information. |
| Office of the Australian Information Commissioner (OAIC) | The Australian government agency responsible for privacy and freedom-of-information functions within its remit. | A source of Australian privacy guidance. |
| Therapeutic Goods Administration (TGA) | The Australian regulator responsible for therapeutic goods within its regulatory framework. | A source of guidance on software-based medical devices. |
| Australian Register of Therapeutic Goods (ARTG) | The register of therapeutic goods included in the register under the applicable Australian framework. | A reference when investigating the regulatory status of relevant medical devices. |
| Medical device software | Software that meets the applicable legal definition of a medical device. Its regulatory status depends on the relevant framework and circumstances. | Software whose intended purpose may bring it within medical-device regulation. |
| Intended purpose | The purpose for which a product is intended, as established by relevant information such as its labelling, instructions, and other applicable evidence. | A factor considered when assessing software under the TGA framework. |
| Compliance | Conformity with applicable legal, regulatory, contractual, or organisational requirements. | A conclusion that requires evidence against the relevant requirements. |

## 6. Technical-Writing Terms

| Term | Definition | Example or context |
|---|---|---|
| Technical documentation | Information that explains how a product or system works, how to use it, or how to maintain it. | User guides, installation instructions, and API references. |
| User guide | Documentation that explains how an intended user completes tasks with a product. | The patient registration guide in this portfolio. |
| Troubleshooting guide | Documentation that helps users investigate problems and identify appropriate next steps. | A guide structured around symptoms, possible causes, and actions. |
| Prerequisite | A condition that must be satisfied before a task can be performed. | Having an authorised account before registering a patient. |
| Expected result | The outcome a user should observe after completing an instruction successfully. | The expected destination after saving a patient record. |
| Source attribution | Identifying the source of information used in a document. | Linking to the original OpenMRS guide. |
| Version-specific documentation | Documentation that explicitly identifies the software version or release to which its instructions apply. | A guide verified against a particular application release. |
| Assumption | A statement accepted provisionally but not yet verified. | Assuming a permission is required before confirming the relevant configuration. |
| Verification | Checking a statement, workflow, or behaviour against appropriate evidence. | Comparing instructions with official documentation or testing them in an authorised environment. |
| Scope | The boundaries of what a document or project covers. | Limiting the registration guide to the OpenMRS web application. |
| Plain language | Communication designed to help the intended audience understand information clearly. | Using direct instructions and explaining unfamiliar terms. |
| Traceability | The ability to connect a statement or requirement to its source or supporting evidence. | Recording which source supports a product-specific instruction. |

## 8. Terminology and Usage Rules

To maintain consistency across this portfolio, the following rules apply:

1. Use **patient record** when referring to an individual record in the system.
2. Use **patient registration** for the process of creating a patient record.
3. Use **web application** and **Android client** explicitly when platform differences matter.
4. Use **authentication** for identity verification and **authorisation** for permission to perform an action.
5. Use **permission** for an allowed action and **role** for a collection or assignment of permissions, where the system supports that model.
6. Use **verified** only when appropriate evidence supports the statement.
7. Label illustrative examples as hypothetical rather than presenting them as actual OpenMRS behaviour.
8. Avoid describing a product as compliant unless the relevant requirements and supporting evidence have been established.
9. Define abbreviations when they first appear in a document, where appropriate.
10. Prefer clear, consistent wording over unnecessary technical jargon.
